# Unified custom cascaded PID controller

## Scope and status

`CascadedPIDController` is the independent Stage 5 control law. It emits
`BodyRateThrustCommand`; the existing adapter converts those commands and the
Crazyflie firmware continues to run the body-rate PID and motor mixer. It does
not call the official hover controller.

Stage 5B is implemented, validated offline, and has one initial powered hardware
experiment. That run showed bounded attitude response and active altitude control
before a 0.50326 m horizontal-displacement safety abort; it did not complete the
full profile. Stage 5C and 5D equations and
configuration gates are implemented so the same controller can be extended
without replacing its architecture, but they are not approved for hardware.
The controller is connected to the dedicated `CascadedStage5BRunner`. Durable
configuration flags in `stage5b_offline_config.json` remain false; per-process
flight authorization is the explicit CLI confirmation and is never inferred
from replay or a previous run.

## Equations and coordinates

All translational states are world-frame SI units, world Z is positive upward,
attitudes are radians, and outputs are body rates in rad/s plus normalized
collective thrust.

Altitude channels:

```
e_z  = z_ref - z
e_vz = vz_ref - vz
u_z  = Kp_z e_z + Kv_z e_vz + Ki_z integral(e_z dt)
T    = clamp(T_eq + clamp(u_z, correction bounds), thrust bounds)
```

The effective altitude correction bounds are the intersection of explicit
correction bounds and final thrust bounds. Conditional integration rejects an
update that pushes a saturated command farther outward and accepts one that
unwinds it. Stage 5B disables `Kv_z` and `Ki_z`.

Horizontal Stage 5D channels use world position and velocity errors:

```
a_world = Kp_xy (p_ref - p) + Kv_xy (v_ref - v)
a_body  = Rz(-yaw) a_world
pitch_ref = atan2(a_body_x, g)
roll_ref  = -atan2(a_body_y, g)
```

Horizontal acceleration magnitude and tilt-reference magnitude are independently
bounded. The attitude loop then uses wrapped yaw error and desired-minus-measured
roll/pitch errors. Output rate limits are applied per axis. The API pitch-command
sign is `-1` because the installed cflib legacy manual-setpoint path negates pitch
while packing; this preserves the previously verified corrective firmware-side
sign. This compatibility detail must be rechecked if the command adapter changes.

## Stage 5B configuration

The checked-in offline configuration uses:

- equilibrium/minimum/maximum thrust: 0.425 / 0.380 / 0.450;
- altitude Kp: 0.10 normalized thrust per metre;
- altitude velocity and integral feedback: disabled;
- roll/pitch/yaw attitude gains: 4.0 / 4.0 / 2.0 s^-1;
- roll/pitch/yaw rate limits: 0.35 rad/s;
- XY feedback: disabled;
- powered-attitude validation and hardware-flight authorization: false.

These retain the earlier limit and gain assumptions; they are not new validated
flight parameters. The file is deliberately named `offline_config`.

## Offline replay result

The 394-sample official-hover recording was replayed through the unified Stage
5B controller. Predicted thrust was 0.417746 to 0.435105, mean 0.424091, with no
altitude saturation. Rate-limit events were roll 3, pitch 14, and yaw 33. Maximum
absolute recorded errors relative to level and initial heading were 0.1222 rad
roll, 0.1478 rad pitch, and 0.5725 rad yaw. The yaw result explains the 33 yaw
limit events and should be reviewed before any powered test; it is not evidence
that the custom yaw loop can recover physically.

The replay uses states generated by the official hover controller. Commands are
not fed into a vehicle model, so it validates deterministic equations, signs,
limits, contribution logging, and file generation only. It is not closed-loop
simulation or flight validation.

## Reviewed powered-attitude validation procedure

This procedure is a prerequisite design, not authorization to execute it.

1. Do not use free flight or an attitude-hold-only takeoff. Use a purpose-built
   restraint/test stand that securely retains the vehicle and limits motion to
   the single axis being evaluated, without allowing propeller contact, vehicle
   escape, cable entanglement, or rebound into the propellers. A hand-held or
   improvised tether is not acceptable.
2. Require a separate explicit authorization for each powered run, an observer,
   eye/face protection, a cleared area, reachable battery disconnect, and the
   supervisor emergency stop. Inspect propellers, guards/fixture, deck, battery,
   radio link, state freshness, and supervisor status before every run.
3. First validate the fixture and logging with propellers removed. Confirm that
   controller configuration has both flight flags false and that no takeoff
   runner is available from the offline replay command.
4. Implement and unit-test a dedicated restrained-test runner before execution.
   It must use a short time limit, explicit axis selection, a reviewed thrust cap
   no greater than 0.45, zero desired angle, contribution logging before command
   transmission, hard limits, and immediate supervisor stop. It must not contain
   an automatic repeat or gain search.
5. Evaluate one axis per explicitly authorized run. Introduce only the fixture's
   small, bounded physical displacement; verify that the measured angle and
   firmware-side commanded body rate oppose it. Begin below lift-capable command
   if the fixture permits useful observation. Never infer a safe value from the
   0.425 equilibrium candidate alone.
6. Acceptance requires correct response polarity for every tested axis, no
   growing oscillation, no unexpected cross-axis command, fresh finite state,
   no supervisor fault, rate commands within 0.35 rad/s, complete logs, and
   successful operator emergency-stop verification. Any ambiguity is a failure.
7. Review the artifact and fixture behavior before changing
   `powered_attitude_validated`. That flag records a human decision; software
   must never set it from replay or automatically authorize a later run.

## Hardware logging and analysis requirements

The eventual runner must log timestamps and phase; full references and measured
state; every altitude, velocity, integral, horizontal, attitude, and heading
contribution; raw and limited body-rate/thrust commands; saturation flags;
supervisor state; state age; loop interval; and persistent abort evidence. The
existing calibration safety limits, explicit per-run confirmation, hard-stop
behavior, and controlled landing policy remain mandatory.

Performance analysis for free flight must report hover altitude RMSE/overshoot,
velocity, tilt, XY displacement, body-rate and thrust saturation fractions,
landing status, deadlines, freshness, and safety events. No replay metric may be
reported as hardware performance.

## Compatibility assessment for later integration

The output type and major state/reference conventions match the frozen outer-loop
boundary. Likely transferable pieces are wrapped yaw error, world-to-body XY
rotation, bounded horizontal acceleration-to-attitude mapping, measured vertical
velocity feedback, conditional altitude anti-windup, and per-axis rate limits.

Integration is not yet proposed. Before touching `OuterLoopPIDController`, Stage
5B, 5C, and 5D need reviewed hardware artifacts, stable landing behavior,
parameter provenance, regression tests against the validated equations, and an
explicit comparison of pitch-sign handling and horizontal mapping. Until then,
`velocity_control_framework/` remains unchanged.
